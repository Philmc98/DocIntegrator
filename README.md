## Event sourcing, Kafka, Redis, ClickHouse

- При **создании/обновлении/удалении** документа:
  - хендлеры команд (`Create/Update/DeleteDocumentHandler`) пишут изменения в БД через `IDocumentRepository`;
  - формируется доменное событие `DocumentEvent`, которое сохраняется в `IDocumentEventStore` (таблица `DocumentEvents`);
  - то же событие сериализуется в JSON и отправляется в **Kafka** (`KafkaDocumentIntegrationService`, topic `documents-events`);
  - событие попадает в аналитическое хранилище **ClickHouse** через `ClickHouseDocumentAnalyticsWriter`.
- При чтении документа по Id:
  - сначала выполняется попытка чтения из **Redis** (`IDocumentCache` / `RedisDocumentCache`);
  - если кеш пуст, данные читаются из PostgreSQL/MS SQL, мапятся в DTO и кладутся в Redis.

Такой сценарий демонстрирует:

- использование **event sourcing** и отдельного **event store**;
- интеграцию через **message broker (Kafka)**;
- разделение **OLTP (PostgreSQL / MS SQL)** и **OLAP (ClickHouse)**;
- применение кеша (**Redis**) для ускорения чтений.

## gRPC и микросервисы

- В `DocIntegrator.Api` добавлен gRPC-сервис `DocumentGrpcService` (описан в `Protos/documents.proto`):
  - метод `GetDocumentById` поверх существующего CQRS-слоя (`GetDocumentByIdQuery`).
- gRPC-вызовы живут рядом с REST-контроллерами, что демонстрирует:
  - единый Application-слой для разных транспортов (REST/gRPC);
  - готовность выносить функциональность в отдельные микросервисы.
